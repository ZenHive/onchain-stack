## Findings

### F1 — CHANGELOG gap in `onchain_tempo` (fixed)

`Transaction.sender/1` changed observable behaviour (a high-s envelope used to recover a
wrong address; it now recovers the signer) and the moduledoc, `@doc` and README were all
updated — but `packages/onchain_tempo/CHANGELOG.md` was not touched, and the package has no
`[Unreleased]` section at all. `CLAUDE.md` § "After every task" makes the CHANGELOG entry
part of the task, and reviewers are told to reject on it. This is the only unreleased `lib/`
change in the package since v0.10.0, so the entry would have been lost at the next release.

**Fixed:** added an `## [Unreleased]` / `### Fixed` entry stating the defect, the curvy#8
cause, the low-s pre-normalization, and the two non-claims the source docs also make (`raw`
is not rewritten; recovery ≠ broadcast acceptance).

### F2 — a real cross-package finding was deleted with the report dump, with no task to carry it (filed as task 9006)

36a9d91 correctly removed `packages/onchain_tempo/curvy-recovery-report.md` — a stray
working file that does not belong in a published package. But that file was the only record
of the call-site audit task 8014's third acceptance criterion required, and it named a site
that is **still unfixed**:

> `cartouche/lib/cartouche/recover.ex`, `recover_public_key_from_digest/2` — Direct
> `Curvy.recover_key/3` call does **not** normalize first. […] follow-up required.

Verified against the current tree: `recover.ex:126-130` pipes the caller's signature straight
into `Curvy.recover_key/3`, so it carries the identical curvy#8 defect — and unlike the
onchain_tempo site it is the *shared* recovery API, reached by `recover_public_key/2`,
`recover_eth/2`, and `Cartouche.Transaction.V1/V3/V4/V_2930.recover_signer`, all of which
take signatures from outside the library. There is a trap that makes it more than a
copy-paste of the 8014 fix: cartouche's own `Recover.normalize_low_s/1` sets `recid: nil` on
purpose (the signing path re-derives it), so reusing it at the recovery boundary would break
recovery instead of fixing it.

**Filed as task 9006** — `Normalize high-s signatures at Cartouche's recovery boundary`,
phase 2000 / bundle `cartouche_correctness_010`, `[D:3/B:6/U:5]`, marker `security`,
assignee `cursor` / `cursor-grok-4.6-high`, `depends_on = [2134]` (2134 is in flight on the
same file — do not dispatch both against that write set concurrently). The task also carries
the second, lower-risk site the deleted report named, `Onchain.AA.recover_address/2`, as a
fix-or-justify criterion. Not fixed inline: signing/recovery is critical tier with a >=95%
coverage gate and it is a different package from the landed range.

### F3 — `onchain` and `onchain_js` could not resolve their own dep tree from their committed locks (fixed)

The lock lines in 1551570 are not incidental. `ex_keccak` became a **runtime** dependency of
cartouche in 54539cb (keccak moved onto the Rust NIF), and a path-dep consumer must carry its
sibling's deps in its own lock. onchain_tempo's lock was repaired as a side effect of task
8014 — but the same hole was left open in two other packages:

- `packages/onchain/mix.lock` — missing `ex_keccak` **and** `rustler_precompiled`
- `packages/onchain_js/mix.lock` — missing `ex_keccak`

Since no package's `check.dispatch` / `ci` alias runs `deps.get`, a cold tree (fresh clone,
un-warmed harness worktree) fails those gates with `ex_keccak: the dependency is not locked`
before a single test runs — exactly the failure the 8014 agent hit in onchain_tempo. It is
invisible on a warm developer checkout, which is why it survived.

**Fixed:** ran `mix deps.get` in both packages. The diff is purely additive — two entries in
onchain, one in onchain_js, no existing entry upgraded — and both resolve to the same versions
already locked by cartouche, onchain_tempo and onchain_aave (`ex_keccak 0.7.8`,
`rustler_precompiled 0.9.0`). Validated: `mix compile --warnings-as-errors` now passes cold in
both packages (exit 0).
