## Upstream issue draft

Title: recover_key/3 uses pre-normalization recovery ID for high-s signatures

## Bug

In curvy 0.3.1, `recover_key/3` returns a different public key for the valid complement-s encoding of a signature.

The struct clause binds the effective recovery ID before `Signature.normalize/1`. Normalization replaces high s with n - s and flips the struct's recovery ID, but `Point.from_signature/3` receives the old bound ID. The current main branch has the same code.

## Minimal reproduction

With `{:curvy, "== 0.3.1"}` installed, run this in IEx (only Curvy and OTP are needed; the private scalar 1 is a public test value):

```elixir
alias Curvy.{Key, Signature}
key = Key.from_privkey(<<1::256>>)
message = "high-s recovery reproduction"
low = message |> Curvy.sign(key, compact: true) |> Signature.parse()
n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141
high = %{low | s: n - low.s, recid: Bitwise.bxor(low.recid, 1)}
IO.inspect({
  Curvy.verify(low, message, key),
  Curvy.verify(high, message, key),
  Curvy.recover_key(low, message).point == key.point,
  Curvy.recover_key(high, message).point == key.point,
  Curvy.recover_key(Signature.normalize(high), message).point == key.point,
  Curvy.recover_key(Signature.to_der(high), message, recovery_id: high.recid).point == key.point
})
```

Observed on Elixir 1.20.2 / OTP 29:
```
{true, true, true, false, true, false}
```

Expected:
```
{true, true, true, true, true, true}
```

Both forms verify against the original key. Low-s recovery works; high-s recovery silently returns a well-formed wrong key. Pre-normalizing the struct works around it. The last element also reproduces the bug for DER with an explicit recovery_id option.

## Suggested fix

Resolve and validate the effective recovery ID (including the option override), put it on the signature, normalize, then pass the normalized signature's recovery ID to Point.from_signature/3. Merely reading the normalized struct's ID without first applying the override would leave the DER/option path incorrect.

This is a recovery correctness defect; comparing the recovered key to an expected signer rejects the equivalent high-s encoding. This reproduction does not demonstrate a forgery: callers can already supply arbitrary (r, s, recovery_id) triples.
