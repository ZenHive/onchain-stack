## Superseded — read this before trusting the sections above

Two entries under "Reviewed clean" were wrong, and the CHANGELOG/@doc text
written by findings 1 and 3 described behaviour that has since been replaced.
Corrected in `rpc: decode eth_fillTransaction from the spec `tx` object, not
geth's raw` (Tasks 125 + 126), after five adversarial cross-family review rounds
probing live nodes:

- **"Geth `{raw, tx}` still prefers `raw`"** — preferring `raw` was the defect,
  not the safe path. `eth_fillTransaction` returns an *unsigned* transaction,
  but geth serializes it into `raw` using the canonical *signed* wire format
  with a zero signature. Those bytes cannot be told apart from a signed
  transaction, and re-encoding the decoded struct produced a payload whose
  signature recovers to an unrelated address (reproduced against a live node:
  signer `0x63Cc…`, recovered `0x79EB…`). `tx` — the field `execution-apis`
  requires — now wins.
- **"`V1.encode/1` treating nil as 0 is the minimum"** — it was a silent
  wrong-address hazard. `Cartouche.Transaction.V1` has no `chain_id` field; it
  holds the chain id in `v` until a signature replaces it, which is EIP-155's
  `[chain_id, 0, 0]`. Encoding `nil` as `0` emitted `[0, 0, 0]`. `V1.t()` is
  non-nilable again and `encode/1` no longer coerces.

Task 126, filed here as a discovery, is closed by that same commit — with its
third acceptance criterion deliberately overruled: a legacy fill without a
chain id is now refused rather than encoded, because `[0, 0, 0]` is not a valid
pre-EIP-155 payload either (that is a six-field body).
